Back to the snapshots

Snapshot {{.Snapshot.ShortID}} from {{when .Snapshot.Time}} (host {{.Snapshot.Hostname}}{{range .Snapshot.Tags}}, {{.}}{{end}}).

{{- if .Incomplete}}

The last restore of this stack did not complete. This restore continues it: only missing and changed files are downloaded{{if not .Import}}, and no safety snapshot of the partly restored directory is taken (the one of the incomplete restore is the way back){{end}}.

{{- else if .Import}}

The stack directory does not exist on this host yet: the restore creates it. Nothing is stopped or replaced.

{{- else}}

The stack is stopped and its directory is restored in place: files that differ from the snapshot are rewritten, files that are not in the snapshot are deleted. Changes made since the snapshot are lost from the live stack.

{{- end}} {{- if .ForeignHost}}

This snapshot is from host {{.Snapshot.Hostname}}, not from this host {{- with .ThisHost}} ({{.}}){{end}}. Check before starting the stack: numeric user and group ids are restored as they were; ports, external networks and absolute paths outside the stack directory in the compose file may not fit this host; only bind mounts inside the stack directory are in the snapshot (named volumes are not). New backups of this stack are made under this host's name.

{{- end}}
{{- if .Import}}

Leave it stopped while you move a stack: restore again later (in place, only changed files) with newer snapshots of the source host, and start it with the last one, after the final backup there.

{{- else}} {{- if $.User.IsAdmin}} {{- else}}

The current state is backed up first (safety snapshot).

{{- end}} {{- end}}

Only files that differ from the snapshot are downloaded and rewritten (same size and modification time count as unchanged). If the restore fails half-way, the stack stays stopped and partly restored, and nothing starts, backs it up or changes it until a restore completes; restoring again continues where it stopped.

Image versions

Pinning uses the image digests recorded in the snapshot's metadata.txt. Services built locally cannot be pinned and use compose.yml. If a pinned image can no longer be pulled, the restore is aborted and the current stack is started again. compose.yml is not changed: a later docker compose up uses the tags again.

Restores of a stack that is not running (like this first restore of a moved stack) do not count against the limit of jobs running at the same time, so a long one does not hold up scheduled backups.
